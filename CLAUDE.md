# KoeStudio

Windows desktop drawing and painting program, aiming to be a full-purpose tool in the spirit of Clip Studio Paint. See README.md for the user-facing feature list and the roadmap below for what comes next.

## Workflow (follow this in every session)

- **Runs straight from this folder.** The Desktop and Start-menu shortcuts (`KoeStudio.lnk`) and `Run KoeStudio.lnk` start `KoeStudio.exe` (a committed launcher, see "Server and desktop window" in `docs/architecture.md`), which runs `pythonw app.py` from the project folder. There is no installer and no build step for day-to-day use: every saved change is live the next time the app is opened, or straight away after a reload.
- **Reload key:** F5 or Ctrl+R in any screen saves pending work, then reloads the page so edited `web/` files take effect (`reload()` in `js/app.js`; the open screen and artwork are remembered in `sessionStorage`). Changes to `app.py` need the app restarted.
- **The user's data lives outside the project folder.** Artwork: `Pictures\KoeStudio` (`<id>.koe`, `.thumbs/`, `.backups/`, `.deleted/`, `Exports/`). Window storage (tool settings, colours) and `error.log`: `%LOCALAPPDATA%\KoeStudio`. Never write user data into the project.
- **Never build installers or release packages (nothing for others to install), and never publish a GitHub release, unless the user asks.** The committed `KoeStudio.exe` launcher is not one of these: it just starts `app.py`. Finish changes in source, run the tests, and commit.
- **Testing must not disturb the user:**
  - **Nothing pops up on the desktop.** Test the UI with `python app.py --browser` in Claude's built-in browser pane, or start the real window with `--hidden` (never shown). Don't launch the visible app while testing.
  - **Sound is muted.** Always start test runs with `KOE_MUTE=1` (or `--muted`). `js/mute.js` then silences every audio entry point (media elements, Web Audio, speech), so it also covers sound code added later. Any new sound must still play through the normal browser APIs so the mute catches it.
  - **Scratch data only.** Point test runs at a scratch folder, never the real `Pictures\KoeStudio`:
    `KOE_ART_DIR=<scratch>/art KOE_APP_DIR=<scratch>/app KOE_MUTE=1 KOE_PORT=8790 python app.py --browser`
  - **Looking at the UI:** `node tools/ui_shot.mjs <url> <steps.mjs> <out-folder> [w] [h]` drives a headless, muted Edge over the DevTools protocol and saves screenshots; nothing appears on the desktop. The steps module gets `evaluate(js)`, `shot(name)`, `wait(ms)`, `navigate(url)`. Keep step scripts and screenshots in the scratchpad, point the URL at a scratch test server, and read the PNGs to check layout changes before calling UI work done.
  - When the browser pane is hidden it may not paint or fire ResizeObserver, and its viewport can be 0×0. Give the tab a size with `resize_window` (e.g. 1400×900, reset to `desktop` afterwards), reload, drive it with `javascript_tool` (dispatch `PointerEvent`/`KeyboardEvent`; after Ctrl+0 the view is `zoom = min((vw-80)/W, (vh-80)/H)`, centred) and check results through the saved files (`.thumbs/<id>.png`).
- If the folder or Python moves, recreate the shortcuts with `powershell -ExecutionPolicy Bypass -File tools\make_shortcut.ps1` (`-LocalOnly` makes only the one in the project folder).

## Before calling a change done

1. `npm test` and `npm run check` pass. New pure logic gets tests in `tests/<area>.test.mjs` (server: `tests/test_server.py`, brush import: `tests/test_brushes.py`), with expected values worked out by hand, not copied from output.
2. UI changes have been looked at in a scratch test run (screenshots with `tools/ui_shot.mjs` or the browser pane, see above).
3. **Changelog:** every user-visible change gets a line in `CHANGELOG.md`, under today's date (newest first) and `New`, `Faster` or `Fixed`. One short plain sentence per change, no code names; skip notes, tests and internal tidying.
4. **Guide:** a new or changed feature also gets a line in the right page of `GUIDE` in `js/guide.js` (Help → Guide, F1), and a new shortcut goes in `SHORTCUTS` there (tool keys are listed from `TOOLS` by themselves). Plain words, short sentences, numbered steps for how-tos, a `tip` paragraph for the one thing worth remembering, and a picture (`guidepics.js`) where seeing it explains it faster than words. A new or changed brush setting also gets its notes on the **Special brush settings: notes and tips** page (`brushnotes`): what it is for, good values, and what it doesn't go with.
5. **Notes:** a new subsystem, or a change in how an area works, updates its section in `docs/architecture.md`. Only rules that apply everywhere go in this file.
6. Commit the change with its changelog line (see Repo).

## Where things are

Detailed notes per area (data shapes, function names, how each feature hangs together) are in **`docs/architecture.md`**. Read the section for the area before changing it.

- **`app.py`**: stdlib `ThreadingHTTPServer` on 127.0.0.1 (port 8770, or the next free one) serving `web/` and a small JSON API (`/api/...`), shown in a pywebview (WebView2) window. Flags: `--browser` (serve only), `--hidden` (window never shown), `--muted`. Env: `KOE_ART_DIR`, `KOE_APP_DIR`, `KOE_PORT`, `KOE_MUTE`. `brushimport.py` reads Procreate, Photoshop, Clip Studio Paint, GIMP and Krita brush files.
- **`web/`**: vanilla ES modules, no framework, no build step. Edit and reload.
  - `js/app.js` start-up, the gallery and the tabs of open artworks; `js/api.js` every call to the server; `js/ui.js` shared UI helpers (`esc`, `toast`, `modal`, `menu`, `confirmBox`, `promptBox`, `store`); `js/mute.js`.
  - `js/views/gallery.js` the start screen; `js/views/editor.js` the drawing screen (viewport, pointer input, painting, undo, autosave, menus, `onKey`). Editor features live in mixins assigned to `Editor.prototype`: `layerops.js`, `selecttools.js`, `canvasops.js` and the `*tools.js` / `*tool.js` files in `js/views/`. Side panels: `colorpanel.js`, `layerpanel.js`, `navpanels.js` (they change the document only through editor methods).
  - `js/doc.js`: the document (`Doc`, layer tree of `Folder`/`Layer`/`Mask`, `composite()`, save format, `sanitizeDoc`).
  - The other modules in `js/` are pure logic without the DOM (brush maths, fill, filters, transform, rulers, tree, colour, file formats, ...), tested from `tests/`.
- **`tools/`**: `ui_shot.mjs` (headless screenshots), `check_js.mjs` (`npm run check`), `make_icon.mjs`, `make_shortcut.ps1`, `register_koe.ps1`.

### Rules that cross features

- **Text, vector and fill layers** keep their pixels as a rendering of their data (`renderTextLayer`, `renderVector`, `renderFillLayer`). Change pixels only through `this.target(verb)`, which refuses them (offering Rasterize) unless asked with `{ read: true }` / `{ vector: true }`; whole-canvas changes, flips and merges call `textsIn(rasters, m)` so the text follows or is dropped (and comes back on undo). Vector objects are immutable, and a line's brush is always looked up through `brushOf(v, s)`.
- Anything that draws the live stroke (`live.canvas`) goes through `liveSource(live, r)`, which applies the brush texture and the dual brush.
- New drawing tools pass their stamps through `symmetryStamps` so the symmetry ruler works.
- Any change of canvas size goes through `reshapeCanvas(label, w, h, paint)`, passing its `m` so guides and rulers follow.
- A new filter is an entry in `FILTERS` (`filters.js`) with a pure function and a test.
- Gradients: always pass `this.userGrads()` to `gradientStops`.
- Floating windows use `placeFloating` / `bindFloatingHead` (`reftools.js`); dialogs use `modal` from `ui.js`.
- **Several editors exist at once** (one per open artwork tab, the hidden ones suspended; see app.js). Editor code finds its elements under `this.root`, never with `document.querySelector`, and anything kept in `store` that the editor caches is re-read in `resume()`. The canvas can be split in two panes (`splitview.js`): use `this.viewport` / `this.view` / `this.overlay` (always the active pane), never a fixed `.ed-viewport` lookup.

### How painting works (keep to this when adding tools)

- A stroke is drawn into the shared **stroke canvas** at full strength; `this.live = {layer, canvas, alpha, mode}` makes `composite()` show it on its layer with the tool's opacity while drawing. On pen-up `commitStroke()` merges it into the layer (`source-over`, `destination-out` for erasing, `source-atop` when the layer's alpha is locked) and records an undo patch of just the changed rectangle. Opacity therefore never builds up within one stroke; density (`flow`) does.
- New paint-like tools should fill the stroke canvas, call `this.sel.clipCanvas(this.strokeCtx, rect)` so the selection is respected, then `commitStroke()`; fills, Delete and Alt+Del with a selection all work this way.
- **Selections** are undo steps (`changeSelection(label, fn)` stores before/after mask snapshots: the selected part's alpha bytes, read from the in-memory mask, never a canvas). They are not saved with the artwork.
- **GPU memory:** a canvas that is dropped keeps its GPU memory until garbage collection, which a small JS heap runs rarely. Free big canvases you are done with by setting `width = height = 0` (read undo snapshots, a closed editor's canvases in `freeCanvases`). Don't draw dab by dab with a blend mode other than source-over / destination-out on a doc-sized canvas: the GPU copies what is under every dab (combined brushes blend once per read in `strokeOf`).
- **Transform** (`this.xf`): `beginTransform()` lifts the selected pixels (or the whole layer) into `xf.src`, keeps the rest in `xf.base`, and redraws the layer live on every change (`renderTransform`). `applyTransform()` records one undo step for the layer and the selection; `cancelTransform()` puts the pixels back. **Distort** (`startDistort`, or Ctrl+drag a corner) replaces the affine `xf.t` with `xf.quad` (four doc points for the source corners nw, ne, se, sw): `drawWarped` maps `xf.srcData` through `warpImage` (inverse `homography`, bilinear, in transform.js) into the bounds of the quad, redrawn at most once per frame (`setQuad`); the selection mask is warped the same way on apply. While it is active, clicks on the panels/menus apply it first (`finishTransform`), saving waits, and only `onTransformKey` keys work.
- **Layers, folders and masks:** tools never touch `doc.active` directly; they ask `this.target(verb)` for the raster to change. It returns the layer, or its mask while `this.maskEdit` is on, and refuses (with a toast) hidden layers and folders without mask editing. Paint on a target with `this.inkFor(t)` (masks always get black) and `this.strokeMode(t, erase)`. A mask's alpha is how much is **hidden** (Clip Studio Paint style: painting hides, erasing reveals); `composite()` applies it with `destination-out`. Anything that touches every canvas (canvas size, flip canvas) uses `doc.rasters()`, which includes masks; per-node operations use `nodeRasters(node)` (a layer with its mask, or everything in a folder). Transform takes a layer's mask along (`xf.linked`: lifted and drawn with the same geometry, restored and recorded with the layer) unless the mask itself is being painted on; the Move tool moves a layer with its mask too.
- Every change goes through the history: pixel changes with `pushPatch(layer, rect, before, after)`, structural changes with `structural(label, do, undo)`. Layer visibility is deliberately not an undo step.
- After any change call `changed(rect)` (or `changed(null)` for everything): it recomposites, redraws, refreshes layer thumbnails and schedules the autosave (800 ms after the last change).
- **Rendering is incremental.** `updateComp(r)` queues region r for recompositing (`this.compQueue`) and adds it to `this.dirty`; `flushComp()` does the compositing once, and runs before anything draws or reads `this.comp` (`render`, the eyedropper, `sampleData`, the Navigator), so several pointer moves in one frame cost one composite. Call `flushComp()` before any new reader of `this.comp`; `requestRender()` draws once per frame and `render(region)` repaints only the whole screen pixels that region covers (clip snapped to device pixels, so no anti-aliased edges blend twice). The background, paper shadow, white paper and checker depend only on the view and live in `this.paperLayer` (drawn by `drawPaperLayer` on full renders, copied for partial ones). A partial redraw must equal a full one pixel for pixel; `setView` and `resize` do full renders. `drawOverlay()` only schedules `paintOverlay()` for the next frame, so pointer moves cost one overlay redraw per frame; layer thumbnails refresh at most every 150 ms. The composite canvas has no `willReadFrequently` (it is drawn every frame and read rarely).
- Saving re-encodes only layers whose `version` changed (`Layer.toPng`). Raise `layer.touch()` after changing its pixels.
- **Never read GPU canvases in the hot path.** Layers, the composite and the stroke canvas live on the GPU; `getImageData` on any of them makes the browser finish all queued drawing first (it cost 0.5-1.4 s at every pen-up and a stall per dab), and reading the composite or a layer click after click got slower each time. So: `commitStroke`, Move, Clear/Fill layer, Transform and Apply mask keep undo copies with `snapshot(layer, r)` (a GPU canvas copy; `readSnapshots` turns them into ImageData when idle, trimmed to the painted part by `trimmedSnapshot` in `snapshot.js`: {data, box}; `pushPatch` trims ImageData it is given too; put them back with `putSnapshot` / `drawSnapshot`, and count them with `snapBytes`: history entries' `bytes` are getters, `structural` takes a function); Fill and the wand read `compPixels()` (a kept copy of the composite, refreshed where `flushComp` recomposited, by compositing that part into a canvas in memory; `referencePixels()` likewise while the reference layers' versions stay; both dropped when another tool is chosen); the eyedropper composites its few pixels; selection changes read back only the area they can reach (`Selection.refresh(area)`, `combine(mode, draw, area)`; snapshots keep their outline, so undo reads nothing); PNGs over a megapixel are encoded in `pngworker.js` from an ImageBitmap (`canvasToDataUrl`); tools that change pixels dab by dab (Smudge, Liquify, the retouch tools) read and write through a `PixelCache` (`pixelcache.js`, via `directpaint.js`: tiles read once when first touched, changed tiles written back per pointer move, the first-read pixels kept for the undo step, `endDirect` at pen-up). New dab-by-dab tools should do the same. Any other read of a layer, mask or the stroke canvas goes through `readPixels(canvas, x, y, w, h)` (doc.js: copied into a `willReadFrequently` canvas and read there; `getImageData` on the GPU canvas itself makes the browser move it into memory for good, and every later redraw uploads it again: 20 layers read once by the Move tool's Ctrl+click made each redraw 80-150 ms instead of 15); the PixelCache and `layersAt` (all pixels copied side by side into one small canvas, read once) do the same. While a stroke or a dab-by-dab gesture runs, `flushComp` passes `composite` a `keep = {except}`: screentone and effect layers other than the one painted are drawn from 256 px tiles (`keptLook` in doc.js, worked out once and kept per layer until its version, canvas, tone, effects or mask change) instead of a readback per redraw. Never draw a GPU canvas into a `willReadFrequently` canvas that is read often: from then on every read of it (and of any canvas drawn from it) costs ~0.5 ms; keep what goes into it in memory too (see `Painter.mem`). Note: reading the same untouched GPU canvas twice can give values 1 apart on semi-transparent pixels (the browser moves it to memory after the first read), so compare pixels only after a first read.
- **Zoomed out, the screen is drawn from `this.mips`** (the composite at 1/2, 1/4, ...; `mips.js`): `updateMips(n)` redraws only `this.mipDirty` (set by `flushComp`) in each level with plain bilinear halving, and `render`/the Navigator draw the level from `mipLevel(scale)` with `imageSmoothingQuality = 'low'`. Never draw the composite downscaled with 'high' or 'medium' quality: the browser then rebuilds mipmaps of the whole composite on every change (20 ms frames and 100+ ms hitches on a 3000 x 2000 canvas). Anything that replaces `this.comp` resets `this.mips = [this.comp]`.

### Conventions

- **Save format:** add new fields with a default in `sanitizeDoc` so old `.koe` files keep loading. Never break old files; bump `FORMAT_VERSION` and convert if a field changes shape. Version 2 (folders, masks, `activePath`) reads version 1 files (flat `layers`, `active` index) unchanged.
- **Escaping:** use `esc()` for anything user-supplied that goes into HTML.
- **Storage:** `store(key, value)` in `ui.js` wraps `localStorage` (`koe.` prefix) and never throws.
- **Shortcuts:** follow Clip Studio Paint where it has a convention (P pen, B brush, E eraser, G fill, M selection, W magic wand, U ruler, I eyedropper, H hand, Space pan, Alt eyedropper, Q quick mask, [ ] size, X swap colours, Ctrl+T transform, Ctrl+2 snap to rulers). Ctrl+R stays the reload key.
- **Tools sharing a key:** give them the same `key` in `TOOLS`; repeated presses take turns (`toolForKey`), as G does for Fill and Gradient.
- **UI layout:** the tool bar is grouped by `group` in `TOOLS` (a separator between groups). The **Tool property panel** (`.ed-left`, next to the tool bar) shows the current tool's settings, one compact row each (label | slider | value); for paint tools it shows only `BASIC_PAINT` plus a **Brush settings…** button; the floating Brush settings window (`renderBrushWindow` in `brushtools.js`, state in `koe.brushWin` = {open, x, y, page}) has a page per `SETTING_GROUPS` entry (Paint, Tip, Pen pressure, Stroke, Variation, Texture) under a stroke preview (`drawBrushPreview`: `previewPath`/`previewSettings` in brush.js, dabs from vector.js `strokeStamps` with a fixed seed, so the preview is the real pipeline; redrawn on every setting or colour change). The Gradient tool's panel starts with a colour strip (`drawGradientStrip`). Both are built by `settingsHtml`/`bindSettings` in `editor.js`; `showSetting(k)` copies a changed value into the other one, and `renderToolProps()` redraws both. Other tools get one flat list. Keep labels short and put the explanation in `SETTING_HINTS` (shown as a tooltip). The right side holds Color and Layers. Side panels fold by clicking their heading (`koe.folded`). Menu items with `checked` get a tick column. The `[hidden]` attribute is forced to `display: none` in `app.css`, because button styles would otherwise override it. Tool keys live in `TOOLS`; other keys are commands in `COMMANDS` (`shortcuts.js`, the user can change them) run by `acts` in `onKey`.
- **Icons:** add SVG paths to `icons.js`. The app icon is a chubby cow ("koe") holding a paint palette and brush, drawn in `tools/icon.svg` in the style of the user's BiggTaal and Varken Sketchpad pigs (soft flat shapes, no tile, same eyes and cheeks); `tools/make_icon.mjs` renders it through headless Edge into `web/icon.ico` (PNG entries, 16-256) and `web/icon.png`. The window, taskbar, shortcuts and `.koe` files use `web/icon.ico`; the launcher embeds it.

## Gotchas

- If the port is taken the server moves to the next free one and prints the URL (`Serving http://127.0.0.1:<port>/`); read that line instead of assuming the port.
- Editing files that contain backslashes (`.ps1`, docs with Windows paths) through a Python string in a shell heredoc silently turns `\r`, `\t`, `\x` and similar into control characters. Use the Edit tool, or build backslashes with `chr(92)`, and re-read the result.
- Use `127.0.0.1`, not `localhost` (IPv6-first lookup makes every request slower).
- The pywebview window keeps localStorage in `%LOCALAPPDATA%\KoeStudio\webview` (`private_mode=False`); without it tool settings are forgotten each launch.
- `setPointerCapture` throws for pointers the browser no longer tracks; keep it in a `try`.
- Big canvases are memory-heavy: one 4000×4000 layer is 64 MB, and every full-layer undo step holds two copies. `History` drops old steps past 600 MB.
